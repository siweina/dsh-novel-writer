技术文档

当前版本 6.7.0 · 更新记录见 CHANGELOG（下方「版本说明」）

dsh-novel-writer 的 20 个工具全部在本地运行，不使用在线大模型：所有指标由规则统计与本地 ONNX 推理得出。本组页面面向二次开发与集成方，逐工具说明参数契约、计算原理、约束边界与源码位置。

阅读约定

每个工具页固定按以下顺序组织，可以跳读：

  • 参数：名称、类型、是否必填、语义与校验方式；
  • 输出结构：返回体字段与渲染层行为；
  • 计算原理：公式、词表、阈值与取舍，尽量给出可直接对照源码的表达式；
  • 约束与边界：对调用方模型的限制、被静默跳过的情形，以及跨版本不可比之处；
  • 源码位置：lib/*.js 中的对应实现。
关于数值。从 v4.3.0 起，本插件做了一轮口径整修（统一句末符、清洗动作词表、抽象度改最长匹配、修饰密度增加停用词、六维基线 μ=0 改绝对尺度判定等）。同一本书在新旧版本下的报告数值不可直接比较，涉及具体差异的页面会单独标注。

  • 6.7.0 · 2026-10-20 面板视觉全面改版：只改长相与说法，功能面不动

    起因是三条用户反馈：① 不好看 ② 太杂、功能难找 ③ 描述看得半懂不懂。本版只改网页端面板——lib/client.js 的渲染层、tools/client-src/V6-components.css（4.6 KB → 19.4 KB 的视觉系统）、图标源，以及同步更新断言的 test/client-test.mjs。功能面完全不变：8 个视图一个不少（features / tools / baseline / creation / reports / model / lexicon / diagnose），ALL_TOOLS 仍为 20，controller 的 api.* 语义与后端路由零改动。五条设计原则：① 一个页面只讲一件事（标题告诉你在哪，正文只放这一页的内容，不重复全局状态）；② 安静的默认态（开着的开关不再整行变蓝、也不再贴「已开启」——开关本身就是状态；颜色只留给「需要注意」与唯一主操作）；③ 说人话（描述写「对你有什么用」，工具 ID novel_xxx、参数 action=audit 与内部术语不进主文案，最多收进「说明」展开区或 tooltip）；④ 一种卡片、一种行、一种分区标题（全面板只用这三种积木，不再出现虚线框、无阴影框、蓝色胶囊标题等第 N 种容器）；⑤ 路径与维护信息往下沉（文件路径、数据目录、state.json 统一收进页面底部的「存储位置」折叠区，一个页面只出现一次）。具体变化：删掉每页的大 Hero 卡与子页的蓝色胶囊标题，主页只在标题下留一行副标题，分区标题改为 12px 灰色小标签；首页按「写作资料 / AI 行为 / 功能与工具 / 记录与维护 / 高级」分区，原来独立的「书库统计」卡并进「写作资料」卡底部的一行书库概况（「书库 N 部 · M 章 · X 字」，点开是每本书一行，含「7 天未动」）；工具行统一由 PreferenceRow 承载，导航行行尾是「计数 + ›」；标题、按钮与分组名不再使用彩色 emoji，改为线性图标（图标源 52 个键、每个工具行一枚专属图标）；阈值行的 slider 辅助输入一并移除，每维只留「低于 / 高于」两个百分比输入框。升级须知：无需迁移——不新增配置文件、不改书库格式、不改任何工具的参数契约；面板布局与导航有调整，如果你依赖旧的操作路径，按新界面的中文标签找一次即可。所有既有行为断言（剪贴板三条降级路径、reqId 过期丢弃、破坏性操作二次确认、hook 稳定性）一条没删。设计规格全文见仓库内 tools/UI-REDESIGN.md（16 KB：工作纪律、设计原则、视觉系统、信息架构、文案风格）。

  • 6.6.5 · 2026-10-19 情感复杂度与置信度联动：不可采信时不再给顶格结论

    起因是一句用户反馈：「写作插件用情感曲线测试我的某些小说时会直接爆掉」「第一章的情感复杂度会直接爆掉」。核查结论是不是崩溃，是输出自相矛盾：同一份返回体里一边写着 confidence: "low" 与「检测到高密度 R18/生理描写…请勿采信」的 caveat，另一边照样给出 complexity: { score: 0.6, level: "high" }——下游只要读 level 就会得出「情感复杂度高」，而这个结论已被工具自己否定。实测（书库里的《棍妹》第一、二章，R18 密度 8.99‰ / 9.77‰）：两章都判 level: "high"，而两章的 confidence 都是 "low"。本版让 emotionComplexity(perChapter, reliability) 接收可靠性信号（{ polluted, pollutedBy, noData }，由 analyzeText 在算完污染与零命中判定后传入，经 emotionalQuantification 透传）：level 降级为 "unknown"（新增取值，此前只有 low / medium / high），并新增 reliable（boolean）与 reliabilityNote（固定说明，可采信时为空串）；score 数值保留，但 reliable: false 已标明它的地位。触发条件三类：污染（R18/生理描写 ≥ 1.5‰、或战斗/爽文 ≥ 3‰、或恐怖/疯狂 ≥ 3‰，阈值与词表都是既有实现、本版未改）、无数据（全文零情感词命中）与无 clean 数据（stats.length === 0，覆盖「只命中弱情绪词、clean 一个强词都没有」的情形——这一条由文档负责人独立实测抓出后于本版内一并修掉，同一早退分支不再给 low + reliable: true）；三条的 score 0 都表示「没测到」而不是「情感简单」。真凶之一在渲染层：lib/core.js 的【情感量化】段此前打印 JSON.stringify(q.complexity).slice(0, 120)，而 reliable / reliabilityNote 排在对象末尾、必然被 120 字符截掉，于是「本项不可采信」永远到不了渲染文本；现在改成可读的一行（- 复杂度: <score>（<level>）熵 X/Y，多样性 N，主次 A↔B（k），章间漂移 有/无（基准 …）），并在 reliable === false 时单独起一行写出 reliabilityNote；novel_style_report 的渲染此前完全没有这一项，本版一并补上。如实交代：本版只做了 P0（可信度联动 + 渲染补齐），原计划的 P1「用 clean 计数重算复杂度」经核查已经满足（perChapter 传的本来就是 cleanScoresOf 聚合的 clean 计数，实测第二章 complexity.dominant = anger 与 cleanDominant 一致、而 raw dominant 是 joy），因此不写成「本版新增」；R18 / 高生理描写文本的情感维度本来就不适用，本版做的是「别在不适用的语料上硬给一个高置信度的数字」、不是「让插件准确判断 R18 的情感」，这类文本建议改用节奏 / 爽点 / 对话密度等维度；阈值（1.5‰ / 3‰）未调；情感复杂度没有「正确值」（score 是熵归一化 0.5 + 多样性 0.25 + 主次冲突 0.25 的启发式聚合），本版只是让它在不可采信时不再冒充结论。工具数与参数契约不变（20 个）。另：CACHE_VERSION = PLUGIN_VERSION，分析缓存跟着插件版本号走，所以升级会自动失效旧口径的结果、不需要手动清缓存。详见 novel_sentence_analysis。

  • 6.6.0 · 2026-10-15 可观测性与诊断：本地事件日志 + 第 20 个工具 novel_diagnose

    起因是一句用户反馈：「有些错误光看提示看不出来，能不能加日志」。本版加了本地事件日志与诊断报告，但刻意不做成「给作者看日志文件」——作者不会去读 .jsonl，真正的消费者是替他操作的 AI。新增第 20 个工具 novel_diagnose：读日志 + 做五处体检——书库根、书库内容（书数/章数/字数/解析不出章号的文件/过短章，只统计不读正文）、插件数据目录（应有子目录、JSON 能否解析、zstd 压缩缓存、0 字节、超大与读不出的文件）、语义引擎（惰性探测，不加载模型）、开关与状态快照（哪些工具/功能被关了、总开关在哪一档、lastRoot 是否失效）——把近期调用与降级失败、「工具 × 书名」反复出问题的组合、高频失败类型、可执行建议与「本次覆盖与未覆盖」聚合成一份中文报告（report / events / clear；days 默认 7、上限 90）。工具调用审计在注册层统一包一层，20 个工具一处覆盖（含诊断自身，不散落埋点），只记工具名、安全参数摘要（书名/章号/action 等定位字段 + content/text 的长度）、耗时、状态与错误 code。静默失败的留痕是选择性的：6 个服务端模块里 catch 点 163（块级 } catch 161 + 链式 .catch( 2；旧稿的 164 把 core.js 注释里引用的写法也算成了代码，属口径过计），另有 84 处 logEvent( 调用点——这两个是不同总体：84 处里 77 处落在 catch 体内（＝有留痕的 catch 点），其余 7 处根本不在 catch 里（书库根轨迹 resolveRoot / noteRoot 共 6 处 + 工具调用审计 installToolAudit 1 处，它在 finally 里），所以静默的 catch 点 = 163 − 77 = 86（旧稿的「静默 80」是拿 84 减 164 得来的，会少算 6 处；分 7 类，理由是"不存在/空是常态、已如实披露、重抛由审计层记、纯清理、允许的探测、有意不记的每项分支、无法区分 ENOENT"）；根解析另加一条只记「可疑决策」的留痕。本版内另修三处契约（都由实测触发）：参数摘要的长度/计数派生键（contentChars / textChars / srcChars / filesCount / chaptersCount / termsCount）与 name 此前漏登记在白名单外被整批丢掉——「只记长度」当时并不成立，现补齐；分享层改为 fail-closed（readLogEvents 只有显式 forShare === false 才返回本地层，其余一律脱敏）；分享层的 redacted: true 由条件性改为恒带（层级标志，不是"有内容"标志）。另有一组 P0 修复：「读不到」不再被说成「没有」——只有 ENOENT 才说「尚未初始化 / 未登记 / 尚未保存 / 无创作资料」，文件存在却读不出来时只说「该文件存在，但读不出来」并给出路径与原因（novel_outline 的 read、开写包的锚包、novel_style_report 的 action=get、连贯性审计的大纲对照四处）。覆盖口径如实交代：四处里三处（创作资料读取 / 风格判断读取 / 大纲对照）端到端生效；锚包那一处在真实工具路径上不可达（内部 try 里全是预读文本上的字符串操作，唯一会抛的 assert 在 try 之外），该分支只有函数级与源码级断言、没有端到端覆盖。另有一条残留同类缺陷（下版处理）：把某章文件换成同名目录后，scanChapters 的 if (!entry.isFile()) continue 会静默跳过它——该章从章表消失、诊断的「读不出来的文件」计数为 0、开写包 degraded 里也没有「读取章节失败」，即这一条路径上「读不到」仍被讲成「没有」。日志落在状态目录旁（~/.dsh/dsh-novel-writer/logs/events.jsonl，512 KB 轮转、留最近 3 正是由正文派生的）——因为值层面的长度 / 标点启发式从原理上无法保证自由文本里不含正文，真正的保证是「离开本机的东西不含自由文本」。报 bug 请用面板「复制诊断包」或 novel_diagnose 的输出，不要直接附本机日志文件。面板新增「诊断」入口（选统计窗口 + 一键复制诊断包，用于贴进 issue）；新增 GET /api/dsh-novel-writer/diagnose 路由，与工具同一实现。本工具不判定对错、也不减少 bug，只让定位变快：静默失败只接了有诊断价值的那部分（「文件不存在」这类正常分支刻意不记），并发/性能只给已记录到的耗时、不做压测，各清单有条数与读取预算上限。工具数 19 → 20，参数契约与书库格式不变。

  • 6.5.5 · 2026-10-11 风格基线可指定范围：按全书 / 按部分，锚点不再跟着 AI 一起漂

    回应 issue #1「风格漂移」：AI 续写每章只参考上一章，从第 2 章起它参考的就是自己的产物；而「六维基线」与「原著锚段」原本都从全书取样——书越长 AI 占比越高，锚点自己也在漂（既测不出对原著的偏移，锚段也逐代变成 AI 的文风）。本版给侧栏「风格基线」面板加上基线范围：按全书（默认，＝旧行为，存量书零迁移）/ 按部分（展开章节选择器，只用勾选的章——是「只用」，不是「优先 + 不够再补」）。正在检查的那一章永远排除（即使它在选中列表里）：拿自己跟自己比必然「完美符合」，比不检查更糟。勾中的章（剔除目标章后）少于 3 章时推荐容差自动放宽到至少 ±25%，所以单章也能当基线；勾中的章若取不到（已改名 / 删除，或正文过短无法测量）会被跳过并如实计数，一章都取不到时回退「按全书」并在返回体里写明原因——两种文案：选择都失效 → 「（自定义选择已失效，已回退全书）」；只选中了本章自身 → 「（选中的章只有本章自身，不能作为自己的基线，已回退全书）」。范围按书保存（<书库根>/.novel-writer/baseline/<书名>.json），与全局的容差设置（styleTolerance）不同层。风格自检 / 开写包 / 改稿台 / 风格画像 / 建章五路同源，baselineScope 的文案随之反映用户的选择（开写包与建章还把范围写进模型可见的渲染文本）。插件不判定「你是否漂移了」（文风本就允许演变，那不可判定），只回答「相对你指定的标杆，这一章偏了多少」。工具数与调用参数不变（19 个），五路返回体各新增两个只读字段：baselineScope（文案）与 baselineMode（all / custom）。

  • 6.5.0 · 2026-10-09 用语审计误报修复：子串守卫、行号定位与分档，并堵住正则回溯

    用语审计此前是纯子串匹配，而禁用词 93% 是 2 字词，于是「里正」会在「这里正是」上误报（实测 19 句无辜句子报出 15 条，其中 14 条是误报）。本版：新增子串碰撞守卫表（紧邻字/序列有实证才挡）、候选改为行号区间定位（不再贴原文，按需回读）、按词长分硬命中 / 待判 / 提示三档（2 字词交给模型读那一行自行判断，明确允许判"不是问题"）、中式基准下禁词与客套词去重（旧版每词报两遍）。安全侧：登记的正则新增静态校验（拒绝嵌套量词与无界通配——实测同类模式在 29 字符上要跑 40 秒）并改为逐句扫描，被拒绝的模式会显式报出而不是静默跳过。新增逐词静音（worldview.allowWords，仅本书生效）。工具数与参数契约不变（19 个）。

工具总览

章节与文稿

novel_books列出章节库中的全部作品，含章节数与总字数。 novel_chapters列出某部作品的章节清单：章号、标题、字数、行数、更新时间。 novel_read按行号分段读取章节正文，返回带行号的内容与字数统计。 novel_new_chapter创建新章节文件，章号可显式指定或自动取下一个。 novel_chapter_brief开写包：一次只读调用装配动笔前的全部材料（承接口、伏笔距离、基线、锚段与骨架、禁用清单）。 novel_import扫描目录自动识别书名与章号并分组，支持复制或移动到书库。 novel_keywords统计中文相邻二字组、三字组与英文词的高频项。

分析与测量

novel_style_report风格画像报告：六维基线 μ±σ、指纹、题材、情感、氛围 12 维与语义距离。 novel_style_check新章与全书风格指纹对照，输出相似度与可执行的偏差清单。 novel_fix_plan改稿台：把风格偏差翻译成按严重度 / 代价排序的待办清单（带段落定位），改完可复测。 novel_sentence_analysis九类句式分布、排列规律、句长节奏、情感曲线与风格指纹。 novel_semantic_search本地向量检索：用自然语言定位全书语义相关段落。

设定、剧情与创作资料

novel_plot伏笔与剧情钩子登记：open / done 状态，scan 自动标注被提及的章节；action: graph 结构视图给出跨章的伏笔生命周期、人物出场矩阵与线索活跃度。 novel_settings人物、地点、道具、时间线、世界观用语规范五张表的增删改查。 novel_lexicon必用词表：把「必须使用的专有名词 / 作者惯用词」登记成表（书级 + 全局两层），动笔前由开写包作为硬清单注入，成稿用 audit 扫覆盖率与「通用词顶替」的行号与原句。 novel_summary章节摘要按章管理，供长篇续写时快速回忆前情。 novel_outline创作资料维护：创作设定、人物、大纲、钩子记录与创作状态卡。

审计与配置

novel_continuity_check三路审计：衔接、OOC 与大纲走偏，输出带原文引用的问题清单。 novel_sentence_config查看与修改工具开关、功能开关、系统提示词档位与场景、风格基线容差。 novel_diagnose诊断报告：读本地事件日志 + 五处体检（书库根 / 书库内容 / 数据目录损坏 / 语义引擎 / 开关快照），聚合「工具 × 书名」反复出问题的组合、高频失败类型与可执行建议；报告只含元数据，可安全分享。

共同约定

书库根目录与路径

所有工具接受可选的 root（含 novels 子目录的目录）。解析优先级：调用参数 root → 插件配置项 → MCP 启动参数 --root → 环境变量 DSH_NOVEL_WRITER_ROOT → 当前工作目录。MCP 形态下，参数里的 root 必须落在启动时 --root 指定范围内；越界时由 MCP 层静默回退到 --root，只写入 stderr 日志，调用方不会收到错误（插件层 resolveRoot 本身不做范围校验，范围校验只在 MCP 层 isInsideRoot 进行）。书名、分类等片段经 sanitizeSegment 过滤，防止路径穿越。

数据落盘

所有派生数据集中写在 <书库根>/.novel-writer/ 下：plots（伏笔）、settings（设定）、lexicon（必用词表）、summaries（摘要）、analysis（分析报告）、audits（审计）、embedding（语义索引）、style-reports（风格画像）。写盘采用临时文件 + 原子替换；失败会抛出 ENOVELWRITEFAIL 而不是静默丢弃。

唯一的例外是 v6.6.0 的事件日志：它写在状态目录旁——~/.dsh/dsh-novel-writer/logs/events.jsonl（受 DSH_NOVEL_WRITER_STATE 覆盖；512 KB 轮转、保留 3 份历史），不在 <书库根>/.novel-writer/。理由很实在：最常见的故障就是「书库根不对」，那时 .novel-writer/ 根本不存在或不可写，偏偏最需要留下证据。日志以元数据为主（工具名 / 书名 / 章号 / 状态 / 耗时 / 计数 / 路径 / 错误 code），但自由文本字段（错误消息等）经收敛后至多保留一句（≤160 字）——所以本机日志里可能出现被错误消息回显的输入片段，该文件不出本机；聚合查看与对外分享见 novel_diagnose（报告与面板「复制诊断包」走分享层，自由文本整体剔除）。

语义引擎的可用性

语义检索、语义风格距离与语义隐性情感依赖随包分发的 bge-small-zh-v1.5 量化模型（约 24MB）与 onnxruntime-web（WASM）。引擎不可用时这些能力自动降级为纯规则模式，其余功能不受影响；返回体会以 skippedDims 或专用文案说明降级原因，而非返回空结果。引擎相关的降级同样会记入事件日志，可由 novel_diagnose 聚合查看（本工具只聚合已记录到的事件，不会主动跑一次推理去探测）。

MCP 形态的边界

包内 mcp/server.mjs 把同样 20 个工具暴露为 stdio MCP 服务器（可用 Streamable HTTP 传输）。协议侧：未知工具返回 -32602（Protocol Error）；支持 2025-11-25 / 2025-06-18 / 2025-03-26 / 2024-11-05 版本协商并原样回显；JSON-RPC 批量请求自 2025-06-18 起按规范拒绝；单行报文上限 4 MiB；novel_import 的 src 默认限制在书库根内，需显式加 --allow-external-src 才能放开。
